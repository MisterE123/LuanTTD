# Stock-assisted next-order export experiment

This is an isolated interchange acceptance test, **not** a general
OpenTTD importer or exporter. It makes a new native 14.1 `.sav` from one
private, stock-generated case. The only authored OpenTTD change is
“No loading” on the supported bus's **upcoming** return order. The
currently unloading order, both destinations and timetable are left intact.
No original save, resulting save or stock assets are stored in the repo.

## What it does

1. The Luanti test genuinely runs the loaded bus in the first-delivery
   fixture, writes its paused replay journal immediately after the original
   riders are discharged, and shuts down. A separate engine boot reopens
   that journal and authors the small upcoming-order intent. It cannot
   author one from the untouched starting state or after the claimable
   fare has settled.
2. Stock OpenTTD 14.1 independently resumes a copy-on-read of the exact
   original. Its paused draft must match the Luanti journal's exact tick,
   vehicle and station IDs, XYZ, track direction/frame, speed/progress,
   age countdown, loading state, delivered units, empty bus, and sole
   pending cargo payment (including its actual owner reference and £9
   route/visual values). The writer aborts if stock misses that tick or if
   anything tested differs. The unsupported parts of the native world are
   **not** fabricated from the visual Luanti overlay.
3. The author changes one byte of the matched native draft, the pinned
   v334 `ORDR` row's stock loading field (0 to 64). It admits only
   the exact known table schema, a supported unchanged-target station
   order, nonshared future slot and no-refit value. The current loading
   order and pending provider state are rechecked unchanged. The author
   does not patch a clock, a cash amount, a delivered counter or an
   original save.
4. Unmodified OpenTTD loads the edited draft and writes its normal save
   file, then a **second** stock process opens that file at the exact
   same paused tick. It resumes, observes the original £9 booked once
   and exactly five already delivered, and observes that the next
   station order activates with No loading. Only then is the new
   output written exclusively to the requested distinct path.

For the stock case here, the loaded original starts at tick **2541**,
arrives at its bay at **2725**, and unloads the five age-3 passengers at
**2726**. The new stock output resumes at **2726**, with zero booked
income and £9 pending. The resumed export posts £9 exactly once. The
existing next order (source order ID 0, station 1) activates with flag
64; its old raw flags were 0. A changed tick after this point reflects
ordinary stock progression. The source SHA is unchanged.

## Why the handoff is before booking the fare

The isolated Luanti trip intentionally freezes unrelated town/station
updates. In the real reference they can change the station waiting queue.
In one exact stock draft at tick 2746, stock boarded 5 while the isolated
trip boarded 8 from its frozen queue. The export **rejects** that
post-boarding handoff; it never invents or replaces that part of the
world. At tick 2726 the single moving bus and unpaid event agree. Stock
keeps ownership of the rest of the world, including the waiting queue
that the later native loading pulse will use.

This proves a very narrow stock-assisted re-export with one actual
played change. It does not prove general stock save migration, use of
other orders/cargo/vehicles, return-leg parity, a second independently
created Luanti world export, or a full-world usable native write path.

## Repeat with a private 14.1 fixture

Use the private save generated by `tests/openttd_save_map.py`
(`--retain-fixture`). See `OPENTTD_FIRST_DELIVERY.md` for the exact
reference capture command. Then:

```sh
python3 tests/openttd_bus_first_delivery.py \
  --luanti /path/to/luantiserver --save /private/stock.sav \
  --reference /private/stock-trajectory.json \
  --emit-order-intent /private/played-order-intent.json

python3 tools/openttd_export_order_experiment.py \
  --openttd /path/to/14.1/openttd --share /path/to/stock-data \
  --source /private/stock.sav --receipt /private/played-order-intent.json \
  --output /private/new-stock-output.sav

python3 tests/openttd_order_experiment.py \
  --source /private/stock.sav --receipt /private/played-order-intent.json \
  --output /private/new-stock-output.sav
```

The stock phases use separate temporary game profiles on a loopback-only
dedicated server and a do-nothing copy of the test AI (no new commands). A
busy machine can overshoot the narrow tick capture; it fails closed
rather than applying an edit at the wrong tick. For the developer fixture,
regenerate a receipt against the same private source rather than hand
editing the receipt, and do not publish its private world or saves.

For the separate exact-tick reroute to a genuinely third station, see
`OPENTTD_THIRD_STOP_EXPORT.md`. The original no-load gate remains unchanged.
